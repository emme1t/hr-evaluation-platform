## 1. 目标与设计决定

项目从本地静态交互 Demo 重建为公司内部使用的云端人事评价系统。主要入口为企业微信认证和工作消息，员工在移动端网页填写评价表；企业邮箱只在企业微信通知失败或人员未完成绑定时发送备用网页链接。

本规格选择以下架构：

- Python Django 单体应用，使用服务端模板和少量原生 JavaScript。
- PostgreSQL 保存业务数据。
- 企业微信 OAuth 确认员工身份，企业微信应用消息下发任务。
- Nginx 提供 HTTPS 入口，应用和数据库通过 Docker Compose 部署。
- 首版不使用微服务、Redis、消息队列或前后端分离 SPA。

当前 HTML Demo 只复用业务字段、页面结构和文案，不直接复制为生产应用。

## 2. 方案比较

### 方案 A：Django 单体应用（采用）

优势：内置会话、CSRF 防护、ORM、数据库迁移和管理能力，适合权限较多但并发不高的内部系统；部署组件少，便于备份、恢复和审计。

代价：现有静态 HTML 需要改造成模板和真实表单，后台业务逻辑需重新实现。

### 方案 B：FastAPI 加独立前端

优势：接口边界明确，后续可扩展独立移动端。

代价：需要维护两套工程、认证状态和部署产物，首版开发与测试成本更高，不符合当前最小化要求。

### 方案 C：继续扩展现有静态 HTML 和 Flask 联调工具

优势：短期演示速度快。

代价：现有 Demo 没有真实接口、数据库、权限和审计基础，继续堆叠会增加上线风险，因此不采用。

## 3. MVP 范围

### 3.1 HR 管理端

- 企业微信身份登录，只有配置为 HR 管理员的员工可进入。
- 花名册批量导入、新增、编辑、停用和审计记录。
- 员工类别维护；员工只能选择已启用类别。
- 同部门和跨部门协作关系按员工编号导入或手工维护。
- 关系导入支持覆盖、追加、去重和预检异常清单。
- 每类员工维护独立评价表，评价项、权重和等级描述可编辑。
- 创建评价项目，冻结当时的模板、人员关系和评分规则。
- 生成评价任务、发送企业微信通知、查看回收进度并重发。
- 查看异常、重新汇总、按被评价人导出原始数据、导出汇总表和异常说明。

### 3.2 员工填写端

- 员工从企业微信工作消息进入，完成 OAuth 后自动识别身份。
- 只显示当前登录员工负责的评价任务。
- 显示被评价人、评价关系、评价项和等级说明。
- 支持自动保存草稿和主动保存草稿。
- 提交前检查所有必填项；提交成功后锁定，不允许重复修改。
- 员工只能查看自己的任务状态，不能查看他人评分或汇总结果。

### 3.3 通知通道

- 企业微信应用消息是默认通道。
- 同一评价人在同一项目有多个任务时，合并为一条项目通知，显示待评价数量并进入个人任务中心，避免逐任务轰炸消息。
- 每次通知记录接收人、任务、时间、结果和失败原因。
- HR 可对未通知或未完成任务单独重发。
- 企业邮箱备用通道发送同一网页入口，不以 Excel 附件回收作为主流程。
- 邮件只发送到花名册中的企业邮箱；备用链接有有效期且使用后失效。

### 3.4 汇总规则

- 默认关系权重为上级 50%、同部门协作 30%、跨部门协作 20%。
- 先计算每种关系组的有效评分平均值，再计算加权总分。
- 任一项目要求的关系组缺少有效表单时，总分保持为空并标记“数据不完整”。
- 空字段、越界评分、重复提交、关系不匹配和未回收任务进入异常清单。
- 项目发送后，模板、关系、权重和计算规则冻结；后续修改只影响新项目。

## 4. 首版不包含

- 云之家登录和消息推送。
- 多公司、多租户或对外客户注册。
- 原生 iOS、Android 或企业微信小程序。
- 员工查看个人评价结果或排名。
- 自动收取邮件 Excel 附件并汇总。
- 复杂审批流、绩效申诉和薪酬模块。
- 微服务、集群、Redis 和消息队列。

云之家可在企业微信版稳定后作为独立扩展，不影响核心评价任务接口。

## 5. 系统边界与组件

### 5.1 身份认证组件

- 接收企业微信 OAuth 回调并校验 `state`。
- 使用服务端保存的企业微信配置换取 `UserId`。
- 通过 `wecom_userid` 映射唯一员工记录。
- 未绑定、停用或不在项目范围的员工拒绝访问并记录安全事件。
- HR 权限由本地角色表控制，不直接依据企业微信部门名称推断。

### 5.2 花名册与关系组件

- 导入文件先进入预检，不直接写数据库。
- 员工编号是业务唯一标识，企业微信 UserId 和企业邮箱分别建立唯一映射。
- 关系只保存员工编号对应的数据库主键，不保存姓名副本。
- 校验不能选择本人、关系内不能重复、同部门关系必须同部门、跨部门关系必须不同部门。
- 人员离职使用停用状态，不物理删除历史评价关联。

### 5.3 模板与项目组件

- 模板支持版本管理，编辑产生新版本。
- 项目创建时复制模板、关系和规则快照。
- 项目状态为草稿、待发送、进行中、已截止、已归档。
- 只有草稿状态允许修改范围；发送后只允许延长截止时间、重发通知或提前截止。

### 5.4 任务与提交组件

- 每一对评价人与被评价人生成一条评价任务。
- 数据库唯一约束阻止同一项目生成重复任务。
- 草稿与正式提交分开记录；正式提交使用事务和幂等键防止重复。
- 任务提交后保存提交时间、客户端类型和模板快照版本，不保存无关设备信息。

### 5.5 汇总与导出组件

- 汇总服务只读取已验证的正式提交。
- 汇总结果保存计算版本、计算时间和输入任务数量，便于审计。
- 原始导出按被评价人组织，并限制为 HR 管理员操作。
- 汇总表沿用经确认的 Excel 模板，只写入既有字段，不擅自增加工作表、公式、列宽或样式。

### 5.6 审计组件

- 记录管理员登录、导入、编辑、项目发送、重发、截止、汇总和导出。
- 记录评价提交状态但不在普通操作日志中记录具体评分内容。
- 审计日志不允许通过普通管理界面修改或删除。

## 6. 数据模型

核心表及约束：

- `employees`：员工编号、姓名、企业邮箱、部门、类别、上级、企业微信 UserId、启用状态。
- `employee_categories`：类别名称、编码、启用状态。
- `evaluation_relationships`：被评价人、评价人、关系类型、有效期。
- `form_templates`：类别、模板名称、版本、启用状态。
- `template_items`：模板、分组、评价项、顺序、权重、等级描述和评分范围。
- `evaluation_projects`：项目名称、时间范围、状态、权重、截止时间和规则快照。
- `project_subjects`：项目中的被评价人及其模板快照。
- `evaluation_tasks`：项目、评价人、被评价人、关系类型、状态、通知状态。
- `submissions`：任务、草稿状态、正式提交状态、提交时间、幂等键。
- `submission_answers`：提交、评价项快照、分数和可选备注。
- `aggregate_results`：关系组均分、加权总分、完整性状态和计算版本。
- `notification_logs`：通道、接收人、发送结果、失败原因和重试次数。
- `audit_logs`：操作者、动作、对象、时间和脱敏后的变更摘要。

员工、任务和提交使用不可猜测的 UUID 作为外部标识；数据库内部可使用数值主键。URL 中不出现员工邮箱、姓名或员工编号。

## 7. 权限和数据可见性

角色：

- `HR_ADMIN`：全部配置、项目、原始提交、汇总、导出和审计权限。
- `HR_OPERATOR`：花名册、关系、模板和项目操作权限；不能管理管理员角色或生产配置。
- `EVALUATOR`：只能查看和填写分配给自己的任务。

每个请求同时校验登录身份、角色、任务归属和项目状态。前端隐藏按钮不能替代后端权限校验。

## 8. 关键业务流程

### 8.1 项目准备

1. HR 导入或更新花名册和企业微信映射。
2. HR 导入协作关系并处理预检异常。
3. HR 维护员工类别和评价表模板。
4. HR 创建项目并查看任务生成预览。
5. 系统冻结项目快照并生成任务。

### 8.2 下发与填写

1. HR 确认任务和通知预览后发送。
2. 企业微信按评价人合并推送工作消息；员工从个人任务中心进入具体评价表。
3. 员工进入网页并完成 OAuth 身份验证。
4. 后端只返回该员工名下任务。
5. 员工填写、暂存并正式提交。
6. 系统锁定提交并更新项目进度。

### 8.3 汇总与导出

1. 截止后系统标记未完成任务。
2. 校验服务识别缺失、重复和异常数据。
3. 按关系组求平均并执行 50/30/20 加权。
4. 缺少要求关系组的员工不生成总分。
5. HR 导出模板一致的汇总表和独立异常说明。

## 9. 异常处理

- 企业微信未绑定：显示联系 HR 提示，HR 后台列出未绑定人员。
- 企业微信通知失败：记录原因，允许重发或切换企业邮箱链接。
- 非任务本人访问：返回无权限页面并记录安全事件，不显示任务信息。
- 项目已截止：禁止保存和提交，HR 延期后才能继续。
- 重复提交：幂等返回第一次成功结果，不生成第二份提交。
- 导入异常：有效和异常数据分离，用户确认后才写入有效数据。
- 汇总依赖缺失：保持总分为空，生成明确异常说明。
- 导出失败：不生成半成品文件，保留错误编号供 HR 查询日志。

## 10. 部署设计

### 10.1 环境

- 开发环境：开发者本机，使用脱敏数据。
- 预发布环境：与生产同版本的独立配置，用于企业微信回调、迁移和验收。
- 生产环境：公司租用云服务器，只开放 80/443；数据库不开放公网端口。

推荐试点配置为 2 核 4GB，正式 400～500 人使用时采用 4 核 8GB 和至少 80GB 磁盘。实际规格在压测后确认。

### 10.2 服务

- Nginx：HTTPS、静态文件、请求大小和安全响应头。
- Django 应用：认证、业务逻辑、页面和管理端。
- PostgreSQL：业务数据。
- 定时管理命令：截止检查、通知重试、汇总和备份检查。

所有服务使用固定版本镜像和健康检查。生产发布先备份数据库，再执行迁移和应用切换。

### 10.3 域名与企业微信

- 使用公司控制的 HTTPS 子域名。
- 中国大陆服务器在正式开放前完成所需 ICP 备案。
- 在企业微信后台配置可信域名、OAuth 回调和应用可见范围。
- 企业微信 Secret 只保存在生产密钥配置中，不进入 Git、日志或导出文件。

## 11. 备份、恢复和运行保障

- PostgreSQL 每日自动备份，备份加密后保存到不同于生产服务器的位置。
- 目标数据恢复点不超过 24 小时，目标恢复时间不超过 4 小时。
- 每月至少执行一次自动备份完整性检查；正式上线前必须完成一次恢复演练。
- 应用日志默认保留 30 天，日志不记录评分正文、Secret、Cookie 或完整邮箱链接。
- 数据保留期限作为生产必填配置；未配置时系统不得进入正式项目发送状态。
- 提供应用、数据库、磁盘、证书有效期和备份状态检查。

## 12. 安全要求

- 全站 HTTPS，Cookie 使用 Secure、HttpOnly 和 SameSite 属性。
- OAuth 回调校验随机 `state`，登录后轮换会话标识。
- 所有写操作启用 CSRF 防护。
- 管理端导入、导出和批量操作进行权限校验和审计。
- 数据库和备份使用云盘或存储侧加密。
- 生产配置通过环境变量或云密钥服务注入。
- 敏感数据不进入 URL、Git、普通日志或错误页面。
- 依赖使用锁定版本并进行漏洞检查。

## 13. 测试策略

- 单元测试：关系校验、任务唯一性、提交幂等、评分平均和 50/30/20 汇总。
- 权限测试：评价人、被评价人、HR 操作员和管理员的数据边界。
- 集成测试：企业微信 OAuth、消息发送、邮件备用、数据库事务和 Excel 导出。
- 端到端测试：项目建立、任务下发、移动端填写、截止、汇总和导出。
- 边界测试：空值、重复、越界评分、部门不符、未绑定、已截止和并发提交。
- 部署测试：迁移、健康检查、备份、恢复和回滚。

企业微信与 SMTP 测试使用测试应用和测试邮箱，不使用生产 Secret。

## 14. 上线门禁和回滚

正式上线前必须满足：

1. 所有自动化测试通过，且无阻断级安全问题。
2. 10～20 人试点完整走通项目创建、通知、填写、汇总和导出。
3. 项目参与人员全部完成企业微信映射；未映射人员有经批准的备用路径。
4. HR 验收汇总规则、Excel 格式、权限和异常说明。
5. 完成数据库备份和恢复演练。
6. 域名、HTTPS、备案、企业微信可信域名和应用权限生效。
7. 数据保留期限、负责人和故障联系人已配置。

每次生产发布保留上一版本镜像和数据库备份。应用异常时回切上一镜像；数据库迁移必须提供向前修复或已验证的恢复步骤，不使用未经验证的反向迁移。

## 15. 分阶段交付

### 阶段一：10～20 人试点

企业微信认证、花名册与关系导入、固定模板、项目任务、合并任务通知、网页填写、企业邮箱基础备用链接、50/30/20 汇总、Excel 导出、审计和备份。

### 阶段二：扩展到约 100 人

增加模板可视化编辑、批量通知重发、企业邮箱备用自动化、异常处理工作台和运维监控。

### 阶段三：覆盖 400～500 人

完成性能验证、批量操作优化、全员企业微信映射、恢复演练和正式运行手册。

## 16. 验收标准

- 企业微信内部员工能够免密码进入，只看到自己的评价任务。
- 转发链接或更换企业微信账号不能访问他人任务。
- 草稿可恢复，正式提交只能成功一次。
- 项目发送后模板和规则保持不变。
- 汇总结果严格按项目冻结的规则计算，缺失关系组时总分为空。
- 导出文件保持确认模板的工作表、列、宽度、样式和已有字段结构。
- 管理员关键操作均可在审计日志中追溯。
- 生产数据库不暴露公网，Secret 不出现在 Git 和日志中。
- 备份可在目标恢复时间内恢复到验证环境。

## 17. Git 与工作方式

- `MAIN` 是正式版唯一开发目录。
- 设计规格存放于 `MAIN/docs/superpowers/specs/`。
- 用户批准本规格后，再生成 `MAIN/docs/superpowers/plans/` 下的实施计划。
- 每个功能遵循测试先行、小提交和验证后完成。
- 功能代码、测试、数据库迁移和对应文档在同一次变更中保持一致。
- 真实数据、配置、密钥、数据库、上传和导出文件永不提交。

## 18. 设计假设

- 大多数参与者是企业微信内部成员；未绑定人员通过 HR 异常清单处理。
- 企业微信管理员能够创建自建应用并授权网页登录和工作消息。
- 公司能够提供域名、云服务器和生产运维负责人。
- HR 是原始评价数据和汇总结果的唯一业务所有者。
- 邮件备用通道发送网页链接，不恢复以 Excel 附件作为主流程。

若以上假设在评审中被否定，应先修改本规格，再进入实施计划。
